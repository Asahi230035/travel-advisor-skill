# Task routing and stopping rules

Work within the **smallest scope that completes the user's request**. Identify the requested artifact: shortlist (`discover`), claims audit (`verify`), option comparison (`compare`), cost review (`budget`), requested plan (`plan`), feasibility inspection (`audit`), or targeted edit (`revise`). A mixed request can use multiple skills internally, but deliver only the scope asked for.

**Mode rules**

| Mode | Minimum useful result | Stop condition |
| --- | --- | --- |
| discover | 2–4 genuine options when available; why they fit and relevant sources | User has a meaningful shortlist |
| verify | Each important claim: supported / contradicted / contested / unverified, source and date | Requested claims are evaluated |
| compare | Normalized terms, advantages, limitations, caveats | User can distinguish trade-offs |
| budget | Fixed costs, reserve, flexible categories, one or more balanced options | Budget question is answered |
| plan | Host agent composes the requested route using accessible current evidence, explains estimated costs, times and uncertainties; see [planning workflow](itinerary-planning.md) | Requested day(s)/trip covered |
| audit | Problems, severity, affected items, minimal repairs | Requested section checked |
| revise | Diff, affected implications, preservation of locked items | Requested change assessed/applied |

Never treat the user's willingness to answer one question as permission to expand the task. If they ask for a comparison only, do not offer an unsolicited seven-day itinerary. When the user has provided a complete comparison, avoid redundant research unless freshness materially changes the result. Answers should be concise by default and expand on request.
